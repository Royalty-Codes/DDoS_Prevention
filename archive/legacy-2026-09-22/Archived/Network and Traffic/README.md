# Network and Traffic: SDN DDoS Dataset and Analytics

This directory is the network experiment layer of the SDN DDoS project. It models an isolated Software-Defined Network (SDN), defines benign and DDoS traffic scenarios, creates flow-window telemetry, and provides the path to collect real OpenFlow observations from Mininet, Open vSwitch (OVS), and Ryu.

The dataset currently generated by the project is a **controlled local-lab profile**. It is statistically generated from bounded scenario definitions so that the analytics pipeline can be developed reproducibly. It is not a packet capture and must not be described as measured Internet traffic.

## What the system does

The project has two related modes:

1. **Controlled profile mode, currently used**: scenario parameters are sampled with NumPy, derived flow-window features are calculated, and the result is saved as Parquet. That Parquet file is also exported to CSV for the analytics notebook.
2. **Real local-lab mode, provided as scaffolding**: Mininet creates a local topology, OVS forwards traffic using OpenFlow 1.3, Ryu acts as the controller, and telemetry can be written as JSON Lines. The current builder does not yet transform those JSON snapshots into the canonical dataset automatically.

Both modes are designed around the same canonical schema so that future measured records can replace controlled records without changing the analytics contract.

## Architecture and data flow

```text
Scenario definitions
	|
	v
Bounded traffic profiles ----> Controlled dataset builder
	|                                  |
	|                                  v
	|                         Canonical flow-window schema
	|                                  |
	|                         Parquet and CSV outputs
	|                                  |
	|                                  v
	|                         PySpark cleaning
	|                                  |
	|                         Spark preprocessing
	|                                  |
	|                                  v
	|                         Plotly exploratory analysis

Real-lab alternative:
Mininet hosts -> OVS switch -> OpenFlow 1.3 -> Ryu -> JSONL snapshots
```

The traffic code enforces the local-only network boundary `10.0.0.0/8`. External targets and third-party reflection services are not part of this project.

## Directory structure

### `config/`

- `experiment.yaml` contains the master seed, rows per scenario, and output locations.
- The default is `seed: 42` and `rows_per_scenario: 10000`.
- The configured Parquet path resolves to `data/processed/sdn_ddos_controlled_lab.parquet` at the project root.

### `traffic/`

- `scenarios.py` defines the traffic classes and their statistical ranges.
- `traffic_generator.py` contains the local-target guard and schedule description helper.
- `traffic_config.yaml` defines the allowed laboratory network, maximum packet rate, and window size.

### `dataset/`

- `schema.py` defines the canonical column order and the accepted labels.
- `labeling.py` validates the scenario label and returns the label plus attack family.
- `feature_engineering.py` converts cumulative counter snapshots into window deltas and rates.
- `dataset_builder.py` samples each scenario, builds records, validates them, and writes Parquet plus JSON metadata.

### `topology/`

- `sdn_topology.py` defines four hosts, `h1` through `h4`, attached to switch `s1`.
- The switch is configured for OpenFlow 1.3.
- `topologies.py` re-exports the topology class.

### `controller/`

- `ryu_controller.py` is an observation-oriented Ryu OpenFlow 1.3 application. It accepts switch feature and state-change events.
- `flow_collector.py` writes timestamped switch snapshots and their flow payloads to JSON Lines.
- `controller_config.yaml` defines the controller endpoint, telemetry interval, and snapshot output path.

### `scripts/`

- `run_experiment.sh` validates the local-only configuration and generates the controlled dataset.
- `start_ryu.sh` starts the Ryu controller.
- `start_mininet.sh` starts the local Mininet topology and connects it to the controller.

## How the controlled dataset is generated

### 1. Scenario plan

`traffic/scenarios.py` creates eleven scenarios. Each scenario specifies:

- label and attack family
- protocol and application
- packets-per-second range
- packet-size range
- flow-count range
- TCP acknowledgement ratio range
- attack intensity
- controller-pressure range

The scenarios are:

| Label | Family | Protocol | Application | Behavioral intent |
|---|---|---|---|---|
| `BENIGN` | BENIGN | TCP | HTTP | Normal low-rate web traffic with completed TCP connections |
| `UDP_FLOOD` | VOLUMETRIC | UDP | UDP | High-rate, connectionless traffic |
| `ICMP_FLOOD` | VOLUMETRIC | ICMP | ICMP | High-rate ICMP traffic |
| `UDP_AMPLIFICATION_STYLE` | VOLUMETRIC | UDP | DNS | High-rate, larger-payload UDP pattern |
| `SYN_FLOOD` | PROTOCOL | TCP | TCP | Many TCP SYN attempts with a low acknowledgement ratio |
| `PING_OF_DEATH_STYLE` | PROTOCOL | ICMP | ICMP | Oversized ICMP packet-size profile |
| `SMURF_STYLE` | PROTOCOL | ICMP | ICMP | High-rate, larger ICMP response-like profile |
| `HTTP_FLOOD` | APPLICATION | TCP | HTTP | High-rate application-layer TCP/HTTP traffic |
| `SLOWLORIS_STYLE` | APPLICATION | TCP | HTTP | Low-rate, many-flow, low-completion HTTP behavior |
| `LAND_STYLE` | PROTOCOL | TCP | TCP | TCP traffic whose real-world form would use matching endpoints |
| `PACKET_IN_FLOOD_STYLE` | SDN_CONTROL | UDP | UNKNOWN | High flow creation and controller-event pressure profile |

The maximum configured scenario rate is 2800 packets per second, matching the limit in `traffic/traffic_config.yaml`.

### 2. Sampling each scenario

For every scenario and every requested row, `dataset_builder.py` uses the seeded NumPy random generator to sample:

- packet rate from the scenario's `pps` range
- average packet size from `packet_size`
- flow count from `flows`
- TCP acknowledgement ratio from `ack_ratio`
- controller proxy pressure from `controller_proxy`
- source host from `h1` through `h4`

The default configuration creates `11 x 10000 = 110000` rows. A row represents one ten-second flow window, not one packet.

### 3. Deriving counters and features

The sampled packet rate is multiplied by the ten-second window and a small random factor between `0.9` and `1.1` to obtain packet count. Byte count is packet count multiplied by sampled packet size. TCP SYN and ACK counts are derived only for TCP scenarios.

The builder constructs a previous counter snapshot containing zeros and a current snapshot containing the sampled counters. `compute_window_features()` subtracts the previous snapshot from the current snapshot. This mirrors how real telemetry would turn cumulative switch counters into per-window measurements.

### 4. Labelling and validation

`label_for_window()` checks that every scenario label belongs to the approved label list and returns its attack family. The builder then validates that the final frame contains the required columns, has no null values, and has non-negative packet rates before writing it.

## Dataset schema: all 28 fields

The canonical order is defined in `dataset/schema.py`. The table below explains what each field means and where it comes from.

| Field | Meaning | Generation source |
|---|---|---|
| `timestamp_utc` | UTC creation time of the record | `datetime.now(timezone.utc)` in the builder; it is generation time, not simulated packet time |
| `experiment_id` | Experiment identifier | Fixed value `mininet_ryu_controlled_v1` |
| `scenario_id` | Unique scenario-row identifier | Built from label, scenario index, and row index |
| `switch_id` | Switch associated with the window | Fixed controlled value `s1` |
| `src_host` | Source Mininet host | Randomly selected from `h1` to `h4` |
| `dst_host` | Destination host | Fixed controlled value `h4` |
| `protocol` | Network protocol | Scenario definition: TCP, UDP, or ICMP |
| `application` | Traffic application category | Scenario definition: HTTP, UDP, DNS, TCP, ICMP, or UNKNOWN |
| `window_seconds` | Duration represented by the row | Scenario base value, currently 10 seconds |
| `packet_count` | Packets observed in the window | Sampled packets-per-second x window duration, with bounded variation |
| `byte_count` | Bytes observed in the window | Packet count x sampled packet size |
| `flow_count` | Flows observed in the window | Sampled from the scenario flow range |
| `packet_rate` | Packets per second | Delta packet count divided by window duration |
| `byte_rate` | Bytes per second | Delta byte count divided by window duration |
| `flow_rate` | Flows per second | Delta flow count divided by window duration |
| `mean_packet_size` | Mean bytes per packet | Byte delta divided by packet delta |
| `tcp_syn_count` | TCP SYN count | Derived from TCP packet count and a bounded SYN factor; zero for non-TCP |
| `tcp_ack_count` | TCP ACK count | TCP SYN count x scenario ACK-ratio sample; zero for non-TCP |
| `tcp_handshake_completion_ratio` | ACK-to-SYN completion proxy | ACK count divided by SYN count, bounded by the scenario profile |
| `flow_table_size` | Approximate active flow-table entries | Flow count x random factor from 1 to 3 |
| `packet_in_count` | Approximate Packet-In events | Flow count x random factor from 0.1 to 2 |
| `controller_cpu_proxy_pct` | Proxy for controller pressure | Sampled from the scenario controller-pressure range; not actual CPU measurement |
| `attack_intensity` | Relative scenario intensity | Scenario definition: 0, 0.5, 0.6, 0.7, or 0.8 depending on class |
| `attacker_count` | Number of attackers represented | Shared scenario base value, currently 3 |
| `background_traffic_level` | Background traffic factor | Random value between 0.1 and 0.6 |
| `label` | Ground-truth traffic class | Validated scenario label |
| `attack_family` | Broad attack grouping | Validated scenario family: BENIGN, VOLUMETRIC, PROTOCOL, APPLICATION, or SDN_CONTROL |
| `data_source` | Provenance of the record | Fixed value `controlled_lab_profile` |

### How the fields group together

- **Identity and provenance**: `timestamp_utc`, `experiment_id`, `scenario_id`, `data_source`.
- **Topology and addressing**: `switch_id`, `src_host`, `dst_host`.
- **Protocol and application**: `protocol`, `application`.
- **Traffic volume**: `window_seconds`, `packet_count`, `byte_count`, `packet_rate`, `byte_rate`, `mean_packet_size`.
- **Flow behavior**: `flow_count`, `flow_rate`, `flow_table_size`.
- **TCP behavior**: `tcp_syn_count`, `tcp_ack_count`, `tcp_handshake_completion_ratio`.
- **SDN control-plane behavior**: `packet_in_count`, `controller_cpu_proxy_pct`.
- **Experimental metadata and labels**: `attack_intensity`, `attacker_count`, `background_traffic_level`, `label`, `attack_family`.

## Real Mininet, OVS, and Ryu path

The real-lab scripts are intended for an isolated Linux or WSL environment.

### Ryu

Run:

```bash
bash scripts/start_ryu.sh
```

Ryu listens for an OpenFlow 1.3 switch connection. The controller application handles switch feature and state-change events and is designed as an observation-oriented starting point.

### Mininet and OVS

In a second terminal, run:

```bash
bash scripts/start_mininet.sh
```

Mininet creates `h1`, `h2`, `h3`, and `h4`, connects each to `s1`, and starts OVS with OpenFlow 1.3. The switch connects to the Ryu controller on `127.0.0.1:6653`.

### Telemetry

`flow_collector.write_snapshot()` appends records like this to JSON Lines:

```json
{"timestamp_utc":"...","switch_id":"1","flows":[...]}
```

The collector output is raw snapshot data. It still needs a normalization step that maps cumulative flow counters into the canonical 28-column window schema. That is the main integration gap between the real-lab scaffolding and the current controlled dataset builder.

## Analytics notebook

The analytics notebook is at the project root as `02_PySpark_DDoS_Analytics.ipynb`. It loads the CSV through Spark, not pandas:

```python
df = spark.read.option("header", True).option("inferSchema", True).csv(str(DATA_PATH))
```

### Cleaning

The notebook:

1. removes exact duplicate rows;
2. casts measurement columns to numeric types;
3. removes rows missing identifiers, timestamps, protocol, or labels;
4. removes negative packet and byte measurements;
5. keeps TCP completion ratios between 0 and 1;
6. reports raw rows, clean rows, removed rows, and missing values.

### Preprocessing

Numerical traffic features are assembled into a Spark ML vector and standardized with `StandardScaler`. `protocol` and `attack_intensity` are transformed using `StringIndexer` and `OneHotEncoder`. Identifiers such as hosts, experiment IDs, and scenario IDs are kept for investigation but are excluded from the feature vector to reduce memorization and label leakage.

## The five visualizations and why they are designed this way

### 1. Class distribution

This is a Plotly bar chart of record count by `label`. It answers the first EDA question: do all classes exist, and is the dataset balanced? The controlled generator deliberately assigns 10,000 rows to each scenario, so equal bars are expected. This is useful for comparing classes, but it is not a realistic deployment prevalence estimate.

### 2. Packet-rate distribution

This is a Plotly box plot of `packet_rate` by `label`, colored by `attack_family`. A box plot is used instead of only a mean because it shows median, spread, and outliers. High-volume floods should occupy higher packet-rate ranges, while `SLOWLORIS_STYLE` is intentionally closer to benign traffic. The plot demonstrates both the usefulness and the limitation of a packet-rate-only detector.

### 3. Bubble chart: packet rate, byte rate, and flow-table size

This Plotly scatter chart uses:

- x-axis: `packet_rate`
- y-axis: `byte_rate`
- bubble size: `flow_table_size`
- color: `label`
- hover data: `attack_family` and `controller_cpu_proxy_pct`

The chart is deliberately multidimensional. Two classes can produce similar packet rates but different byte rates because their packet sizes differ. Bubble size adds the SDN flow-table dimension, revealing profiles that combine traffic volume with many active entries. It is particularly relevant for connecting generic traffic intensity to switch state pressure.

### 4. TCP handshake completion

This is a Plotly bar chart using only TCP records and the mean `tcp_handshake_completion_ratio` per label. SYN floods should show low completion because many SYN attempts produce relatively few ACKs. Normal benign TCP should have a higher ratio. Non-TCP records are excluded because a zero TCP count for ICMP or UDP does not mean a failed TCP handshake.

### 5. SDN controller pressure

This is a Plotly bar chart of mean `controller_cpu_proxy_pct` by label. The field is a scenario-based proxy, not operating-system CPU telemetry. The plot is still valuable because it examines a signal specific to SDN control-plane stress. `PACKET_IN_FLOOD_STYLE` is designed to rank high, and its `packet_in_count` and `flow_table_size` context can be inspected in the bubble chart.

## Outputs and interpretation limits

The generated CSV and Parquet files contain balanced, simulated local-lab observations. Their purpose is to test schema design, feature engineering, Spark processing, visualization, and later model experiments. They do not establish real-world attack prevalence, controller CPU behavior, or classifier accuracy on live networks.

For a measured research dataset, the next engineering step is to collect OpenFlow flow and port statistics from the isolated Mininet lab, calculate deltas over the configured ten-second windows, map the results to this schema, set `data_source` to `real_openflow`, and rerun the same analytics notebook.
